# Upgrade and roll back a Sovrium app

> Move a Sovrium app to a new version safely — back up first, let the boot-time migration run, and roll back by restoring the backup with the prior binary.

Schema migrations are **forward-only**: a released migration is never rewritten, and there is no automatic downgrade. So a safe upgrade always pairs with a backup you can restore.

## Upgrade

Back up first with `sovrium backup` — one archive holding the database, the encryption key, the config and the uploads, taken while the app keeps serving — then move to the new version and restart. The schema migration runs on boot, inside a transaction, before the app serves traffic:

```bash
sovrium backup app.yaml --output /backups/pre-upgrade.tar.gz
sovrium update            # binary install; or: docker pull ghcr.io/sovrium/sovrium:latest
sovrium stop && sovrium start app.yaml
```

If the migration fails, the transaction rolls back and the server refuses to start on an inconsistent schema — you are never left half-migrated.

Visitors' browsers pick up the new version on their own. Pages load the client scripts under names derived from their content, so the first page served after the restart asks for the new scripts and nothing cached from the old version can stand in for them. The old, unhashed names still answer for one release, served so that a browser checks them again on every use. A page that was already open before the upgrade and asks for a part of the old version that no longer exists reloads itself once, then runs the new version. Nobody needs a hard refresh, and there is no cache to purge.

A pre-compiled stylesheet does not survive an upgrade either. `sovrium build` writes the app's stylesheet to `output.css` in the data directory — `.sovrium/output.css` unless `SOVRIUM_DATA_DIR` moves it, or `SOVRIUM_CSS_FILE` names the exact path — and a production `sovrium start` serves that file instead of compiling it, which is what makes a cold start fast, whether or not the app declares a `design`. Its first line, `/*! sovrium-css <hash> */`, records what built it: the engine, its default stylesheet, the design and the component types the app declares. A server that finds a file without that line, or with a hash it does not compute itself — built by another version, for a design the config no longer declares, or before a component type was added — sets it aside: it prints one warning naming the file and ending in the remedy, compiles the stylesheet itself, serves that, and leaves the file where it is. Pages are right from the first request after the restart; only the faster start is lost until you run `sovrium build` again — with the new version, before the restart, is the natural moment.

## Check the config with the new version first

A new version can refuse a config the old one accepted: each release closes mistakes that used to validate and then failed later, or quietly did the wrong thing. Run `sovrium validate` **with the new version, before you stop the old server** — between `sovrium update` and the restart above — so a refusal costs you nothing but an edit:

```bash
sovrium update
sovrium validate app.yaml   # the new version's verdict; the old server is still serving
sovrium stop && sovrium start app.yaml
```

A refusal names the place in the config and, in most cases, what to write instead. Fix it, validate again, then restart. Environment variables are read when the server starts rather than by `validate`, so an invalid one surfaces at `start`, before the app serves traffic. Then read the breaking changes between your version and the new one — `sovrium changelog --since <the version you run>` gathers them in one list.

## Upgrading from 0.38 to 0.39

A data component no longer draws its own controls. The search box, the filter and sort builders, the facets and the export button that a `table` drew above itself, and the search box any data component could draw, are composed on the page instead: each control publishes what it holds on a named channel, and every data component that listens to that channel narrows its rows to match. The library block `block/data-table-toolbar` gives a grid its usual toolbar in one entry. Run `sovrium validate` with 0.39 before you restart: it refuses every key in the table below, naming the place and the replacement. These keys are refused without a release in which they first warned, because their replacement ships in the same release.

### What to replace

| Removed                                                                                                                                                | Replace with                                                                                                                                                                                |
| ------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `toolbar` on a `table` (with its `search`, `filters`, `sort`, `facets`, `export` and `refresh`)                                                        | The library block `block/data-table-toolbar` above the grid, with `dataSource.bindTo` and `sharedFilter: {}` on the grid; the refresh button becomes `dataSource.refreshMode`               |
| `search` on a `table`, `kanban`, `gallery`, `carousel`, `list`, `event-calendar`, `timeline`, `chart`, `kpi`, `form`, `container`, `graph` or `matrix` | A `search-input` with `publishes: { bindTo, param: q }` on the page, or the library block `block/data-table-toolbar`; the component listens with `dataSource.bindTo` and `sharedFilter: {}` |
| `scope: subscribers` on a `search-input`                                                                                                               | `publishes: { bindTo: <channel>, param: q }` on the box instead of `scope`, with `dataSource.bindTo: <channel>` and `sharedFilter: {}` on the data components                               |
| `dataSource.targetId`                                                                                                                                  | The `publishes` of the control that narrows the component, `{ bindTo, field, operator }`, with `dataSource.bindTo` and `sharedFilter: {}` on the component                                  |
| `action: { type: filter, targetDataSource }` on a page component                                                                                       | The `publishes` of the control that narrows the component, `{ bindTo, field, operator }`, with `dataSource.bindTo` and `sharedFilter: {}` on the component                                  |

The last two never did anything: no running app read `dataSource.targetId`, and a button whose action was `type: filter` narrowed nothing. Delete them, or wire the control that was meant to narrow the data as the table describes. The `search` of a `tree` and of a `command` menu are those components' own keys and stay, as does the `filter` step of an automation.

**Two other shapes are refused that used to be accepted.** A row rule using `contains` on a field that holds one value is refused by `sovrium validate` and at startup, naming the field: `contains` in a row rule now tests membership in a field that holds several values, a many-to-many relationship or a `user` field with `allowMultiple`. Use `eq` to compare one value and `in` to compare with a list. And a record sheet's footer `crud` action with `operation: create` is refused, naming the action: create a record with a form instead. See [Table Permissions](/en/docs/table-permissions).

### New in 0.39

- **`tables[].label` and `tables[].labelPlural`** are optional names a person reads, where `name` stays the identifier of the database table and of `/api/tables/{name}`. `labelPlural` names the table as a collection — the operator console's sidebar, table directory and record grid, the command palette's "Create new record in …" action and the weekly summary email — and falls back to `label`, then to `name`; `label` names one record's table, as in a generated edit form's "Edit …", and falls back to `name`. Either may be a `$t:` key. An app that declares neither prints the table's `name` as before. `GET /api/admin/tables/overview` adds a resolved `label` beside `name` in each `by_table` row. See [Tables Overview](/en/docs/tables-overview).
- **`displayName`** is an optional root key for the app's name as people read it, where `name` stays the identifier: `Acme CRM` for `acme-crm`. When declared, `$app.label`, the default home page's heading and title, the operator console's sidebar head and breadcrumb root, and its sign-in card print it; without it `$app.label` and the home page print what they printed before, and the console's sidebar head and breadcrumb the name in title case (`Acme Crm`), as they did. The console's sidebar head and sign-in card draw the app's `design.logo` beside it, or a monogram of the name when no logo is declared, in place of the Sovrium mark. See [App Metadata](/en/docs/app-metadata).
- **Two environment variables set the record budgets**, `RATE_LIMIT_WRITES` (default `120`) and `RATE_LIMIT_READS` (default `600`), both counted in the `RATE_LIMIT_WINDOW_SECONDS` window (default `60` seconds). Each must be a whole number above zero, or the server refuses to start, naming the variable. The next section says what they count. See [Environment Variables: App, Server and Database](/en/docs/env-vars).
- **An automation can invite a person** with the `inviteUser` auth action: the account is created without a password and the app's invitation email is sent, as from the console's Users page. See [Auth Actions](/en/docs/automation-auth-actions).
- **A button opens a table's CSV import** with `{ action: openImport, table }`, drawn only for a reader the table lets create records. See [Interactive Components](/en/docs/interactive-components).
- **A grid can take its columns from a form**: `columnsFrom: { form }` over the admin submissions list gives one column per answer, shown only to an admin on an instance that keeps submission bodies. The admin submissions list takes `reveal=true` under the same gate and reports a `total`.
- **A column or `record-field` can declare `format: duration`**, which prints an elapsed time as one compact figure in the page language, such as `2 min 18 s`. See [Data Components](/en/docs/data-components).
- **A graph can mark the nodes a reader should look at** with `flag: { field, label }`: a node whose boolean `field` is true carries one caution mark, in either layout, and is named by `label` in its row of the accessible table and in its title. A graph read from tables passes a node entry's `flagField` through as `flag`. A flag field the node table does not declare is refused at startup. See [The Graph Drawing](/en/docs/data-components-graph).
- **A command palette keeps its own rows while it searches.** With `search`, the authored `groups` are drawn above the result groups and narrowed by typing, where they used to give way to the results. A group or an item takes `visibility`, and one whose conditions do not hold is left out of the page. An item's `label` and `href` may carry `$query`, the words typed so far, URL-encoded in `href`; such an item shows its `emptyLabel` while nothing is typed, or is not drawn without one. See [Navigation Components](/en/docs/navigation-components).
- **`ai-chat` takes `draftParam`**, a query parameter whose words the chat opens with in its message box, focused and unsent; the parameter with no words still focuses the box. A chat that declares none reads nothing from the address. See [AI Chat](/en/docs/ai-chat).
- **An endpoint form can send on change** with `submitOn: change`, where the default `submitOn: submit` keeps its button. The form draws no submit button; a switch or a select sends the whole form at once, and a typed control sends once typing pauses, or at once when the reader leaves it or presses Enter. A refused change puts a switch or select back to the state last saved. `submitLabel`, `submitVariant` and `onSuccess.reset` are refused beside `submitOn: change`. See [Endpoint Forms](/en/docs/data-components-endpoint-forms).
- **A record sheet's `recordFields` entries and footer `actions` take `visibleWhen`**, the condition a grid's row actions take, read against the open record: an unmet condition leaves the entry or the button out, and the sheet follows the record when a footer action changes it. Hiding is not a permission: a hidden field keeps its value when the sheet is saved. A `visibleWhen.field` the sheet's table does not have is refused at startup. See [Overlay Components](/en/docs/overlay-components).

### Behaviour that changes without a config change

- **Every record write draws on one budget per caller.** A create, an update and a delete under `/api/tables/*` — `POST`, `PATCH`, `PUT` and `DELETE` together — count against 120 writes a window per caller, where 0.38 limited creates alone, at 50, and did not limit updates and deletes at all. A batch request counts as one write however many records it carries, so a client that edits many records sends them through the batch endpoints. A signed-in person reads up to 600 times a window, a ceiling no page reaches; a visitor who is not signed in keeps 100 reads per address; and each API key has its own budget of 300 requests a window to `/api/tables*`, counted by the key even when a session cookie travels beside it. A read of the tables list now counts once where it counted twice, and a `HEAD` request counts as the read it names. A script that writes one record per request faster than two a second meets `429`: raise `RATE_LIMIT_WRITES`, or move it to the batch endpoints. A page that meets the limit says in a toast how many seconds to wait and keeps its rows and selection, and a form posted without scripts returns to its page with that message rather than the raw `429`. See [Security Hardening](/en/docs/security-hardening).
- **The default muted text and field border are darker.** On the default design, light muted text is `oklch(0.52 0 0)` where it was `oklch(0.556 0 0)`, the light field border `oklch(0.65 0 0)` where it was `oklch(0.922 0 0)`, and the dark field border white at 40% where it was 15%, so muted text reaches 4.5:1 against the surfaces it sits on and a field's edge 3:1 against the page. This is a visual change only: nothing in the config changes, and an app whose `design` sets its own `muted-foreground` or `input` colours keeps them. See [Build an accessible app](/en/docs/accessibility).
- **The default destructive red is darker in light mode.** It is `oklch(0.5 0.245 27.325)` where it was `oklch(0.577 0.245 27.325)`, same hue and chroma, so a destructive label drawn on its own tint — a destructive button, badge, menu item or error notice — reaches 4.5:1 over the page, cards and muted surfaces, and the white label of a solid destructive button keeps it too. The dark value is unchanged. This is a visual change only, and an app whose `design` sets its own `destructive` colour keeps it. See [Build an accessible app](/en/docs/accessibility).
- **A `user` field with `allowMultiple` holds a list of people.** It used to store one account; its value is now a list of account ids, read and written as an array by the records API, forms and the MCP tools, and `contains` in a filter or a row rule tests whether the list names a person. The first start of 0.39 converts each such column, even with an unchanged config: the stored account becomes a one-person list, on both database engines. A client that read or wrote the field as one id now reads and writes an array. A rollback restores the backup taken before the upgrade, whose column still holds one account. See [User & Audit Fields](/en/docs/user-audit-fields).
- **The records of a table listed in `auth.scopeTables` are addressed by their text ids.** Such a table is keyed by a generated text id, and 0.38 answered `404` to a read, an update or a delete of one record, skipped every id of a batch update, and sent a form saved without scripts to a `404` page. Each of them now reaches the record, as do the MCP record tools. A many-to-many relationship to such a table now starts on PostgreSQL, and a scope table with a count, rollup or lookup field accepts inserts.
- **A text filter on a relationship matches the linked record's name.** `contains`, `startsWith` and `endsWith` on a many-to-one link compare the typed text with the linked record's display field, without regard to case, and `equals` matches the exact name as well as the stored id; a linked record in the trash, or one the reader's row rules hide, is not matched by name. A client that filtered a link by part of its id now matches by name. See [Filtering, Sorting and Pagination](/en/docs/records-filtering-sorting).
- **`contains` in a page data source's `filter` treats `%` and `_` as the characters they are.** `50%` no longer matches `500 units`, and `a_b` no longer matches `axb`, as in the records API already.
- **Rows checked on a page follow the same row rules as the records API.** A list bound to a table, a hosted form's relationship choices, the comment trigger, the command palette, the MCP tools and a signed-out form submission judge a rule using `contains`, or reading a column one relationship away, the way the records API does, where such a rule used to show no rows on a page.
- **A record write that loses to a concurrent one answers `409`.** On PostgreSQL, when the database aborts one of two transactions waiting on each other — a record write meeting the erasure of the account it names, for example — the losing write answers `409 Conflict`, which the client may retry, where it answered `500`. An account erasure that meets a concurrent write runs again, up to three times, and completes. See [Create, Read and Update](/en/docs/records-crud).
- **A record sheet's footer `crud` action now runs.** A footer `delete` or `update` asked its question and did nothing once it was answered; it now deletes the record the sheet shows and closes the sheet, or writes the action's `data`, and the grid behind it re-reads. A `crud` action carrying its own `confirm: true` in a grid's row or bulk actions, or in a record drawer's footer, now asks before it runs, with its `confirmMessage` or the page language's default question; it used to run on one click.
- **Records name people and linked records.** A `description-list` entry or a `record-field` drawing a `user` field prints the person's name where it printed the account id, and one drawing a relationship prints the linked record's display field where it printed its id. On a page bound to one record, `$record.<field>` in `meta.title`, `meta.description` and an enumerated breadcrumb's labels resolves where it printed the token. A board grouped by a select or status field heads its columns and lanes with the option's label where it printed the stored value.
- **A page that declares no `meta.lang` follows the visitor's remembered language** at a one-segment address such as `/archive`, as every other page already did, and a `bytes` value is written in the page language: a French page reads `1,5 ko` where it read `1.5 KB`. See [Languages](/en/docs/languages).
- **The words the engine writes itself follow the page language.** The operators, range ends, value field and **Apply** button of a filter bar's condition builder and its chips, and its add and remove controls; the note a KPI, chart, calendar, gallery, board, timeline, list or record field shows when its read fails or its binding is missing; the names of a grid's selection checkboxes and the hint on a sortable header; a breadcrumb trail's landmark name and an unlabelled theme toggle; the status a data component announces while it loads; a record sheet's **Cancel**, **Previous**, **Next** and **Open full page**, and the **Cancel** and **Continue** a dialog draws when its config leaves a button label out; and the message of an empty grid bound to a table, which now names that table. They read English on an English page as before, French on a French page, and any of them can be renamed under `languages.translations[<lang>]` with its `sovrium.` key; a label the config writes is still drawn as written. A loading placeholder also carries a `data-loading-status` attribute that does not depend on the language, so a test or script that waited for an English loading text can wait for that attribute to go. The same holds for the rest of the copy the engine writes: what the passkey, single sign-on and account-link forms report; a hosted form's drop zone, user picker and sticky save bar; a record form's upload and delete confirmation; the map's controls; the command palette's own rows and toast; the date and period pickers' defaults; the empty line of a gallery, timeline or chart; the tree's filter and states; the signature pad; an upload's button, drop zone and refusals; a matrix or graph that cannot be read; and every word of the `ai-chat` panel. Each has a `sovrium.` key to rename it. See [Languages](/en/docs/languages).
- **Numbers follow the page language.** A percentage KPI reads `66,7 %` on a French page where it read `66.7%`, with the same precision. A currency field that declares a thousands separator but no `symbolPosition` uses the separator to group the digits and lets the page language place the symbol, so a French page reads `9 600 €` where it read `€9 600`; declare `symbolPosition` to fix it. A formula declaring `format: currency` reads as an amount, in its currency and the page language, in every grid, including one whose column declares no format such as the operator console's records grid, where it printed the bare number. English pages and the records API are unchanged. See [Number Fields](/en/docs/number-fields).
- **Grids fit small and wide screens.** Below 768 px, a grid row opens on a tap — its `onRowClick`, else the first action that only navigates — and the grid draws no action columns, whose actions stay reachable from what the row opens; a grid with nothing to open keeps its action column, reached by scrolling sideways. A grid wider than its container keeps its first column in view as the reader scrolls sideways, casts a shadow at its right edge while columns are still hidden past it, drawn in a stronger tone on the dark theme, and names the full value of a cell whose text is cut off in a tooltip, whether the reader points at the cell or reaches it with the keyboard. A column bound to a `button` field keeps a plain header and offers no sort, since the field stores nothing to order by. See [Data Components](/en/docs/data-components).
- **A password field that sets a password states the rule under it.** Sign-up, a new password from a reset link, an accepted invitation, and an endpoint form field marked `autocomplete: new-password` read "At least 8 characters", with the app's `minPasswordLength`, in the page language; on an endpoint form a larger field `minLength` raises the number, after the field's own `description`. Sign-in and current-password fields state none. When the server refuses a current password as wrong, or a new one as too short, the refusal is marked on that field and the focus moves there, beside the toast. See [Email & Password](/en/docs/auth-email-password).
- **Charts.** A chart declared without a `dataSource` draws its missing-binding notice in the page language, where it failed to mount and drew nothing. A height given to a chart through `props.className` now caps the chart card, with or without a legend, where the plot spilled over the element below. Axis labels take the theme's muted text colour, readable on the dark chart card where they were drawn black. See [Charts](/en/docs/data-components-charts).
- **Record sheets.** A footer action is drawn in the `variant` it declares, where every footer action was a plain bordered button, and as an outline button when it names none. A sheet that creates a record over a table with no `label` is headed **New record** in the page language, where it read the table's raw name. See [Overlay Components](/en/docs/overlay-components).
- **A list value reads as a list.** A record field holding several values separates them the way the page language joins a list, `image/png, image/jpeg`, where they ran together.
- **A KPI and a chart reading the same system endpoint send one request.** Tiles and charts bound to the same endpoint and query share one answer, and identical row reads in flight at the same moment share one request; polls and refetches still ask the server.
- **A link to the console's root keeps its query on the bare address.** `/?q=…` written in a mounted page lands on `/_admin?q=…`, where it landed on `/_admin/?q=…`.
- **`sovrium library add block/app-navbar-command` installs into a project that refuses arbitrary Tailwind variants**, and re-adding a YAML fragment that a formatter only re-quoted or re-wrapped no longer reads as an edit. See [The Library of Ready-Made Pieces](/en/docs/cli-library).
- **The stylesheet's address changes with the engine.** The stylesheet is linked as `/assets/output-<hash>.css` and cached for a year; its hash now covers the engine's version and its default stylesheet as well as your design, so the first page served after an upgrade links a new address and no browser keeps the previous release's stylesheet. Nothing to purge.
- **A pre-compiled stylesheet from another version is set aside.** `sovrium build` now writes `output.css` in the data directory — `.sovrium/output.css` unless `SOVRIUM_DATA_DIR` moves it — or the file `SOVRIUM_CSS_FILE` names, with the first line `/*! sovrium-css <hash> */`, a hash of the engine, its default stylesheet, the design and the component types the app declares. A server that reads the file — `sovrium start` in production, and in development when `SOVRIUM_CSS_FILE` is set — serves it only when that line carries the hash it computes itself. A file without that line, which is every file 0.38 and earlier wrote, or with another hash is set aside and never rewritten: the server prints one warning, ``Pre-compiled stylesheet at <path> was built by a different engine or config; compiling afresh. Re-run `sovrium build`.``, compiles the stylesheet, and its startup report reads `CSS compiled (N KB, stale pre-compiled file ignored)`. So the first 0.39 start of an app built under 0.38 prints that warning once. Run `sovrium build` once with 0.39, or accept one compile at each start until you do. See **Upgrade** above.
- **An app with a `design` is now served from its pre-compiled stylesheet.** Earlier versions accepted the file only for an app declaring no `design`; any other app compiled at every start and the file `sovrium build` had just written for it was never read. The stamp line now decides on its own, so a designed app gets the same fast start. The operator console still compiles its own stylesheet and prints no warning for the app's file.
- **The pre-compiled stylesheet follows `SOVRIUM_DATA_DIR`.** `sovrium build` writes it to `output.css` inside the data directory and `sovrium start` reads it there, beside the database. A deployment that moved the data directory and ran `sovrium build` found the file written to `./.sovrium/output.css` under the working directory, where production never looked; `SOVRIUM_CSS_FILE` still names an exact path when set.
- **Each app's stylesheet holds what its pages use.** It is compiled from a core set, the styles of the component types the app's pages and reusable components declare, and the classes the config writes itself, where 0.38 served every app the styles of every component type. It is still one stylesheet per app, so moving between pages fetches no other, and the core set styles the default home page and the not-found page whatever the config declares. An app that places fewer component types downloads a smaller stylesheet; a page of text no longer carries the grid, calendar or chart styles. Nothing in the config changes and pages look as they did. Two effects follow. The stylesheet's address changes once for every app outside the operator console, and browsers fetch it again because the cache is keyed on the address: there is nothing to purge. And placing a component type the app did not declare before changes the address and the pre-compiled file's hash, so if you ship the file from `sovrium build`, build it again after such a change. The operator console at `/_admin` is still served the complete set. See [Theme Overview & Colors](/en/docs/theme).
- **The default fonts are separate files.** Geist and Geist Mono were inlined into every stylesheet; they are now `woff2` files served under `/assets/fonts/`, named by their content and cached for a year. Every page preloads the sans face unless the design declares its own body or sans family, and the mono face loads only where monospace text is drawn. A static export from `sovrium build` writes them beside the stylesheet: publish the whole output folder. See [Typography](/en/docs/theme-typography).
- **An automation run started by a person reads their email and name.** `{{trigger.user.email}}` and `{{trigger.user.name}}` sit beside the id and the role, and a form submission by a signed-in person now carries `trigger.user` at all; an anonymous submission still has none. See [Auth & Form Triggers](/en/docs/trigger-auth-form).
- **A connection operation's `object` or `array` parameter receives the value a whole template names.** A parameter filled with one template such as `'{{steps.build.quote}}'` receives the object or list, with nested values keeping their types, where it received the text the template rendered to. A template with anything around it still renders to text. See [Connection Operations](/en/docs/automation-connection-operations).
- **An administrator listing access grants on an app with no scope tables receives an empty list** instead of a `404`.
- **Page structure changed for assistive technology.** Each field control carries one id minted for it, where two fields with the same label shared one built from the label; the page search box is a `combobox`; an empty state's title is no longer a heading; a board's column titles are second-level headings; a grouped table row's collapse toggle is a button carrying `aria-expanded`; and a button that opens an address in a new tab says so. A test or a script that found a control by an id derived from its label, or a heading or role these changes moved, finds it by its label or its new role. See [Build an accessible app](/en/docs/accessibility).
- **`sovrium update` reaches GitHub through a spent rate limit.** It sends the token in `GH_TOKEN`, or `GITHUB_TOKEN` when that is unset, to GitHub's releases API and nowhere else, and when the anonymous quota is spent it still finds and installs the newest release, verified as usual. See [Admin & Maintenance](/en/docs/cli-admin).
- **An endpoint form honours `hidden` and `readOnly`.** On a page `form` with `endpoint:`, a field marked `hidden: true` was drawn as an editable control; it is now an `<input type="hidden">` with no control and no label, its value still sent, and a `$session.*` default is still filled in the browser. A field marked `readOnly: true` is shown and cannot be changed: a text control carries the browser's `readonly` attribute, and a `select` or `switch`, which have none, is drawn disabled with `aria-readonly="true"` and still submits its value. A read-only `select` with no `defaultValue` submits the first option it shows. One shape is refused that used to load: a page `form` field that is `hidden: true` and `required: true` with no `defaultValue` is refused when the config is read, with `hidden field '<name>' is required but has no defaultValue: give it a defaultValue or drop required` — give it a `defaultValue`, or drop `required`. The fields of a top-level `forms:` entry are not affected. See [Endpoint Forms](/en/docs/data-components-endpoint-forms).
- **An invitation opens on the operator console.** When the app declares no invitation page of its own, the link in an invitation email opens the console's own invitation page, which a person who is not signed in can open: it names who sent the invitation, the app's display name and the address the account will carry, while the rest of the console stays closed to them. An app that declares its own invitation page keeps the link on that page. See [Invitations](/en/docs/auth-invitations).
- **An iframe can load a page or a file of the same app.** Every response refused to be framed, so an `iframe` whose `src` was a path of the app drew an empty box. An address that an `iframe` on one of the app's pages names by its path now allows framing by the app itself, `frame-ancestors 'self'`; the page holding the frame, and every address no `iframe` names, still refuses every frame. See [Media Components](/en/docs/media-components).
- **An invitation sent from the console grants the least by default.** On the console's Users page, **Invite** opens a dialog over the member list rather than moving to the invitations tab, and its **Role** starts on `viewer`, where it used to start on the first role listed, `admin`. ## Upgrading from 0.37 to 0.38

0.38 takes the names shadcn/ui gives its components, keys and tokens. Run `sovrium validate` with 0.38 before you restart: it refuses every old type, key, value and action in the table below, naming the place and the new spelling. Two names come back with shadcn's meaning: `type: drawer` is now the panel that rises from the bottom edge, and `type: calendar` a month of days to pick a date from. A bare one is the new component; one still carrying the old component's keys — a side panel's `drawerSide` or `drawerSize`, an event view's `dataSource` or `dateField` — is refused key by key, naming `sheet` or `event-calendar`. The utility classes are not refused, and the last two rows answer the two default changes listed first under the behaviour changes below, which apply without a config change. Then read the behaviours below that your app relies on.

### Behaviour that changes without a config change

- **Every app follows the visitor's colour scheme unless it says otherwise.** With no `design.colorScheme`, an app used to stay light unless it declared `darkColors`; it now follows the operating system in every case, and an app that declares no `darkColors` is drawn on the default dark palette of the prebuilt components. To keep an app light, declare `design.colorScheme: light`. A visitor's stored choice from a `theme-toggle` still wins. See [Baseline & Dark Mode](/en/docs/theme-dark-mode).
- **Code blocks come in a light and a dark theme by default.** An app that names no `design.codeBlock.theme` used to draw every fenced code block with `github-dark`; it now draws them with `github-light` in the light scheme and `github-dark` in the dark one. An app that names a `theme` and no `darkTheme` keeps that one theme in both schemes, as before; one that wants dark code blocks everywhere names `theme: github-dark`. See [Spacing, Radius & Elevation](/en/docs/theme-spacing).
- **A `context-menu` opens on a right click over its `children`.** It used to draw a button labelled Menu that opened on a left click; it now draws its `children` and opens where the reader right-clicks them, or after a long press on a touch screen, as the documentation described. A `context-menu` with no `children` draws nothing a reader can open: give it the element the menu belongs to as its `children`. See [Navigation Components](/en/docs/navigation-components).
- **A `navigation-menu` panel is a list of links, not a menu.** An entry with `children` used to open a menu, whose rows a screen reader announced as menu items; it is now a button that discloses its panel, announced as expanded or collapsed, and the rows are links. Nothing changes on screen, and a click, `openOnHover` and Escape behave as before. A test or a script that looked the rows up as `menuitem` looks them up as links, and one that waited for a `menu` checks the entry's `aria-expanded` instead. See [Navigation Components](/en/docs/navigation-components).
- **A table reads a value by its field type when the column names no `format`.** A `currency` cell prints the amount in the field's currency, a `percentage` cell prints it at the field's precision (`25%`), a `created-at`, `updated-at` or `deleted-at` cell prints a date and time in the page language where it printed the stored instant, and an `email` or `phone-number` value is a link. A column that names a `format` keeps it. Page text reads a `deleted-at` field the same way. See [Data Components](/en/docs/data-components).
- **A table's quantities sit on the right.** A `number`, `integer`, `decimal`, `currency`, `percentage`, `autonumber`, `count` or `duration` column aligns its header and its cells to the right, and quantities, dates and times are set in tabular figures. Give the column `align: left` to keep it on the left.
- **A table's option chip with no colour is filled.** A `status`, `single-select` or `multi-select` value whose option declares no `color` is drawn as a grey filled badge where it was an outline. Give the column `badgeForm: outline` to keep the outline.
- **A table's row action asks for confirmation in a dialog over the page.** An action with `confirm` opens a modal alert dialog named by its question, where it used to swap its button for a question inside the row; the row no longer changes size while the question is open, and the page behind the dialog cannot be used until it is answered. A test or a script that read the question inside the row reads it from the page instead. See [Data Components](/en/docs/data-components).
- **`dataSource.pagination.style: infinite` loads as the reader scrolls.** A `gallery` and a `kanban` board that declared `infinite` paged like `numbered` or not at all, and a `list` declaring `loadMore: infinite` showed only its first page; each now draws its first page and loads the next one when the reader scrolls to its end, with a Load more button kept for the keyboard. Declare `numbered` to keep page controls. See [Data Binding](/en/docs/pages-data-binding).
- **Integer options in the published JSON Schema and OpenAPI document carry their range.** Every integer node in the schema `sovrium schema` writes, and in the document `/api/openapi.json` serves, now states `minimum: -9007199254740991` and `maximum: 9007199254740991`, the range an integer keeps exactly in JavaScript, unless the option declares a tighter bound of its own, which it keeps. Validation does not change: the engine already refused an integer outside that range. A tool that compares the schema or the document byte for byte, or a client generated from them, sees the new keywords; regenerate it. See [Validation & Schema Generation](/en/docs/cli-validate) and [OpenAPI](/en/docs/openapi).
- **The migration adds one table, for chat attachments.** The boot-time migration creates `ai_chat_attachments`, which records each file a reader attaches in an `ai-chat` that declares `attachments`; the file itself is stored in the bucket that block names. It stays empty until a chat with an `attachments` block receives a file, it is included in `sovrium backup`, and a rollback that restores the pre-upgrade backup removes it. The files themselves live in the bucket, not in the table: with local storage, `sovrium restore --force` replaces the data directory and they go with it, but with S3 storage a backup lists the bucket's objects without copying them, so a file attached after the upgrade stays in the bucket after a rollback, with nothing pointing at it. Before rolling back an app on S3, note the time of the upgrade and delete the objects under `ai-chat/` written since then. See [AI Chat Component](/en/docs/ai-chat-component).
- **Run history shows the values of variables declared `secret: false`, and no longer masks a short secret inside other text.** A `secret: false` variable set by the environment used to read `***` in step outputs and errors; it now reads as it is, as it already did when its `default` was in force. A value a secret variable also holds stays masked. A secret shorter than six characters is no longer masked inside other text, so a variable holding `3` no longer turns `browser step 3` or a run id into `***`; a value that is exactly a short secret is still masked, and a secret is masked whole even when another secret's value is part of it. Keep real credentials six characters or longer. See [Automation Environment Variables](/en/docs/automation-env-vars).
- **A browser step inside a `path` or a `loop` now fills in its values.** A `browser/run` placed in a `path` branch or a `loop` typed its templates and `$env` references as written; it now fills them in when each step is reached, exactly as at the top level, and `{{loop.item}}` reads the item. A config that worked around this by calling another automation keeps working. See [Browser Actions](/en/docs/automation-browser-actions).
- **A `fill` that cannot set its field now fails instead of reporting `ok`.** A `fill` on a time, date, date-and-time, month or week field now sets the value, where it used to leave the field empty while reporting success. Every `fill` reads its field back, and a field that does not hold the value given — one that keeps fewer characters, or reformats what is typed — fails the step. That includes a site that reformats what is typed, such as a phone mask or a field that upper-cases its input. A run that relied on such a step passing now stops there: check the field on the site.
- **A record write answers before its record automations finish.** A create, update, delete or restore through the records API, a form submission, a form's edit link, the MCP tools and the AI chat now answer as soon as the row is written, and the record automations they start run in the background, where they used to hold the answer until every run had finished — a slow run could end in a `504` although the record was saved. A form's `onSuccess` fires right after the write, and its ledger row reads `processing` until its automations end. A client that read an automation's effect, or the run itself, right after its write must now poll the run history. See [Record & Comment Triggers](/en/docs/trigger-record-comment).
- **An AI action's error now fails its step.** A `generate`, `extract` or `agent` step that met an error — a rate limit, a rejected key, a timeout, a reply `extract` could not parse, a refused tool call — was recorded as completed with the error in its output, and the run went on with empty data; it now fails, so the run stops there, a `retry` policy attempts it again when the error is worth it, and a synchronous webhook answers `500`. To keep a flow that went on after such an error, add `continueOnError: true` to the step and branch on `{{steps.<name>.status}}`. See [AI Actions](/en/docs/automation-ai-actions).
- **A success toast now follows the move it announces.** When a button, row action, menu item, edit form or hosted form shows a success toast and then navigates to another page of your app, the page the reader lands on shows that toast once as it loads; a reload does not show it again. A message you placed on the landing page to make up for the lost toast can go. See [Interactions & Auto-Save](/en/docs/interactions).
- **An edit form in a dialog closes the dialog on every save.** A save that went through the page script, such as one showing a toast beside a `navigate`, used to leave its dialog open; it now closes it, as a plain save always did. Write `onSuccess.close: false` to keep the dialog open. See [Interactions & Auto-Save](/en/docs/interactions).
- **`sovrium validate` refuses an off-site address after an action.** An `onSuccess.navigate` on a button, row action, menu item, endpoint form, file upload or edit form, and a success page `redirect`, written as an `http://`, `https://` or `//` address, is now refused: it was never followed. Use a path on your site, or a link to send the reader elsewhere. See [Validation & Schema Generation](/en/docs/cli-validate).
- **A delete button is shown to the readers the table lets delete.** A `crud` delete button was hidden from everyone as soon as its table declared a `permissions.delete` rule; it is now shown to the signed-in readers that rule admits, and to admins. Check that the rule names only the readers you want to offer it to. See [Table Permissions](/en/docs/table-permissions).
- **A `unique` field ignores the records in the trash.** A value held only by a deleted record can be used again. The first boot of 0.38 replaces each single-field unique constraint with a unique index over the records that are not in the trash: the config does not change and every row is kept. Restoring a deleted record whose value a live record now holds is refused with `409`, naming the field, and the record stays in the trash. An upsert no longer matches a deleted record: it creates a new one. A composite top-level `unique` follows the same rule, while a unique index you declare under `indexes` keeps the shape you wrote, and a key that a `foreignKeys` entry references still counts deleted records. See [Validation](/en/docs/table-validation) and [Soft Delete and Restore](/en/docs/records-soft-delete).
- **An embedded form's title is an `<h2>`.** A form placed on a page with `formRef` titled itself with an `<h1>` unless `props.headingLevel` said otherwise, so a page with its own title had two. It now renders as an `<h2>`, whatever the form's layout; a form on its own `/forms/<name>` page keeps its `<h1>`. Write `props.headingLevel: h1` on the placement to keep the old heading. See [The Form Component](/en/docs/data-components-forms).
- **`$record.<attachment>` is the file's address on a page bound to one record.** On a page whose `dataSource` reads one record, on a `collection` page and in a component bound in single mode, the token printed the stored value; it is now the address that serves the file, as it already was in a list's rows, with the `.key`, `.url`, `.name`, `.size` and `.mimeType` parts. A template that printed the stored value on purpose writes `$record.<attachment>.raw`. In a list's rows, `$record.<attachment>.raw` now prints the stored value where it used to print the file's address. See [Data Binding](/en/docs/pages-data-binding).
- **Engine words and the default auth emails follow the app's language.** On an app whose language is not English, the recorder button and file checks of an attachment field, an empty grid, an auth form's default labels, submit and error summary, a multi-step form's navigation, the file preview toolbar and the close control of a zero-JS dialog now read that language, and the default invitation, password reset, email verification and magic-link emails are written in the recipient's chosen language, else the app's default. An app that declares no languages reads exactly what it read before. Each word can be renamed under `languages.translations.<lang>.sovrium.<key>`; a custom `auth.emailTemplates` entry is unchanged. See [Languages](/en/docs/languages).
- **`noindex: true` now wins over `robots`.** A page that sets both renders `noindex` followed by its other directives, so `robots: follow` reads `noindex, follow`, as the sitemap already treated it. A config with `noindex: true` beside a `robots` string that asks for indexing (`index` or `all`) is refused by `sovrium validate` and at start-up, naming both keys. See [SEO & Metadata](/en/docs/seo-meta).
- **A form submission or an automation press sent twice with the same idempotency key is answered once.** A hosted form and a form placed on a page now carry a hidden `_idempotency` field, and a page's automation buttons send an `Idempotency-Key` header with each press. Within five minutes, a repeat of a successful request from the same caller, with the same key and values, receives the first answer with `Idempotency-Replayed: true` and stores or runs nothing; the same key with other values is refused with `422` `IDEMPOTENCY_MISMATCH`. A request with no key is processed as before. A client of your own that reuses one key for different submissions must now send a new key for each. See [Form Submissions](/en/docs/form-submissions) and [Interactions & Auto-Save](/en/docs/interactions).
- **`sovrium reload` applies the whole edit, on a server started with or without `--watch`.** It used to refresh the `X-Sovrium-Config` header and print `Configuration reloaded` while an edited automation, table or page kept running as before. It now does what `--watch` does with a save: a change to pages or copy is swapped in place, and a change to `tables`, `automations`, `auth`, `agents`, `connections`, `env`, `analytics` or `buckets` restarts the server on the same port, closing open connections. The command waits for the server's verdict and prints it, exits `1` when the server refused the configuration or could not boot it, and the status file records every reload. A script that ran `reload` after editing a restart-class key and then restarted anyway can drop the restart. See [Server Lifecycle](/en/docs/cli-lifecycle).
- **`sovrium bundle` and `sovrium deploy` carry the files declared under `assets`.** They travel as `project/<path>` in the archive, listed in its manifest, so a deployed app that reads an email template or a document model boots. A host running an engine older than 0.38 refuses a bundle that carries an asset; one without assets is unchanged. See [Bundle an App](/en/docs/bundle).
- **`sovrium library add` follows your sign-in page, and re-adding a block with new parameters updates it.** The auth blocks now link to the page `auth.loginPage` names instead of `/sign-in` when you set no path, and a block another one requires takes the parameters they share (the password-reset screens share their app mark). A fragment installed with 0.38 records its parameters on a second header line; adding it again with other `--set` values rewrites it while you have not edited it, instead of refusing. A fragment installed before 0.38 counts as unedited when it is what its block writes today with the default parameters, whatever version its first line names; it used to be refused as edited after any upgrade. See [The Library](/en/docs/cli-library).

## Upgrading from 0.34 to 0.35

Run `sovrium validate` with 0.35 before you restart, then read the behaviours below that your app relies on.

### Behaviour that changes without a config change

- **An `http/*` request the outbound guard refuses fails once, and is no longer retried.** A request to a private address, with a scheme other than `http` or `https`, with a malformed `url`, or whose `https` connection cannot be secured now fails the step with `error.code` set to `blocked` or `tls`, and a retry policy no longer tries it again. A step that relied on its retries for such a URL now fails on the first attempt: fix the URL, or the certificate on the other side. See [HTTP & Webhook Actions](/en/docs/automation-http-actions).
- **An empty template value written to a number or a link column is stored as NULL.** A record step writing an empty value to a number, currency, percentage, progress, rating, duration, relationship or user column used to store `0`, or fail on the foreign key; it now stores NULL. A text column keeps the empty string. Review any filter or formula that counted on the `0`. See [Record Actions](/en/docs/automation-record-actions).
- **JSON text written to a `json` column is stored as the object or array it spells.** A record step writing the text of a JSON object or array to a `json` column now stores the parsed value, as the records API does. Text spelling a scalar (`"42"`, `"true"`) is still stored as text, and rows written before the upgrade are left as they are.
- **A record trigger no longer hands an automation the fields only admins may read.** The row, the previous row and the related rows a record trigger expands now leave out every field whose read permission is admin-only. An automation that read such a field from `{{trigger.data.…}}` now reads nothing there: read the row through a `record/read` step instead.
- **A `relative-time` column reads in the largest whole unit.** A cell reads `now`, a number of minutes or hours, `yesterday`, or a number of days, where it used to count whole days only. See [Data Components](/en/docs/data-components).
- **`toolbar.export: false` also removes Export selected.** A table grid that turns its export off no longer offers to export the rows a reader ticks. A grid that leaves `export` undeclared keeps the selection export.
- **A bulk action's confirmation buttons are translated.** The two buttons read in the page's language through the string catalogue (`Confirmer` and `Annuler` on a French page), where they always read in English. Name them yourself with `confirm: { message, confirmLabel, cancelLabel }`.
- **A chart over hours or minutes labels its ticks as times of day.** With `xAxis.format: date`, a chart bucketing by `hour` or `minute` writes each tick as its time of day in the operator timezone, and adds the day and month when the chart spans several days. See [Charts](/en/docs/data-components-charts).
- **Telemetry ingest no longer counts against `API_IP_RATE_LIMIT`.** The paths a telemetry webhook trigger serves are refused by their own per-project and per-address budgets instead, so a busy reporter no longer spends the ceiling your other API clients share. See [Telemetry Triggers](/en/docs/trigger-webhook-telemetry).
- **Run history can be shortened.** `SOVRIUM_AUTOMATION_RUN_RETENTION_DAYS` deletes the runs that ended more than that many days ago, once a day; unset, every run is kept, as before. A trigger's `history: 'minimal'` keeps each run it starts without its trigger data or its steps, and replaying such a run without new trigger data answers `409`. See [Automation Runs](/en/docs/automation-runs).
- **An invalid `BROWSER_*` value stops the start, even while the browser is off.** If your environment already sets a variable whose name starts with `BROWSER_`, check it against the accepted values before you restart; the refusal names the variable and what it accepts. The checks between the browser's and the document renderer's Chrome settings apply only once the browser is on. See [Environment Variables: Browser Automation](/en/docs/env-vars-browser).
- **The migration adds one table, for browser sessions.** The boot-time migration creates `browser_sessions`, which holds the signed-in sessions a browser step saves, encrypted with the instance key. It stays empty until a step saves one, it is included in `sovrium backup`, and a rollback that restores the pre-upgrade backup removes it.
- **A public form placed on a page with `formRef` now renders for signed-out visitors.** A form that declares no `access`, bound to a table whose `create` grant does not admit visitors, rendered an empty container on the page while `/forms/<name>` served it and accepted the submission. The page now draws it as its own page does, and a submission from it is stamped with `system`. Give the form an `access` block if it was not meant to be public.
- **A `visibility.record` gate on a checkbox compares yes or no.** `eq: true` now keeps a component on the ticked records and `eq: false` on the others, on SQLite as on PostgreSQL; on SQLite both used to match no record, and `neq: true` every record. See [Component Modules](/en/docs/component-modules).
- **A number or a word compared with a checkbox reads as yes or no, on either database.** In a `dataSource.filter`, a `visibility.record` gate, a collection page's `collection.filter`, a form's choice-list `filter`, a table view's `filters`, the `filters` of a lookup, rollup or count, and a records API `?filter` written as JSON, `1` and `"true"` now mean ticked and `0` and `"false"` unticked. On SQLite a collection page filtered with `value: true` on a checkbox used to answer 404 for every record; it now shows the ticked ones. On PostgreSQL a filter written with `value: 1` or `value: 0` on a checkbox used to fail the page with a server error, and a gate written with `eq: 1` matched no record; both now behave as on SQLite. A table view, lookup, rollup or count filtered that way on PostgreSQL used to stop the app from starting, and a JSON `?filter` used to answer a server error; on SQLite, the same filters written with `"true"` or `"f"` used to match no record. Prefer `true` and `false`. See [Data Components](/en/docs/data-components).
- **A multi-select prints its labels in a description-list field entry and in a list row.** A `description-list` entry naming a multi-select with `field` draws one chip per label on SQLite too, where it printed the stored text (`["red","blue"]`), and a `record-field` inside the row of a bound `list` prints the labels — and any other value formatted by its type, a date included — exactly as the same `record-field` prints them on a record page. See [Display Components](/en/docs/display-components).
- **The audit log loads on SQLite once an entry carries details.** On SQLite, `GET /api/admin/audit-log` and the admin audit log tool of the MCP server failed with "Failed to build audit-log response" as soon as the trail held an entry with details — a role change is the first one most instances record. Both now answer, and each entry's `metadata` reads as the same object it reads on PostgreSQL. Nothing was lost: the entries were stored intact and read back in full.
- **A structural `timeline` draws its markers.** A `timeline` with `children` and no `dataSource` now draws a marker on the rail beside each child, as documented. A page that drew its own dots inside the children shows both: remove the hand-drawn ones.
- **A `fetch` body value that is exactly `$record.<field>` over a list sends the list.** On a multi-select, a field holding several attachments or any other list column, such a value used to reach the server as the items joined into one text (`"a,b"`); it now arrives as a JSON array (`["a", "b"]`). This applies to every `fetch` action's `body`, and to the `inputData` an `automation` action sends from a table row. An endpoint that parsed the joined text must now accept an array. A reference inside a longer string (`'tags: $record.tags'`) is unchanged and still writes the joined text. See [Interactions](/en/docs/interactions).
- **The migration adds four columns to `auth.device_code`.** The boot-time migration adds `redirect_uri`, `device_name`, `return_code_hash` and `requested_at`, all nullable, which hold a one-click sign-in while it waits for approval. A rollback that restores the pre-upgrade backup removes the columns.
- **`sovrium login` signs in with one click by default.** It opens the approval page in your browser, and the browser hands the answer back to the CLI through a listener on `127.0.0.1`, where it used to print a code to approve. Pass `--device` to keep the code; the CLI keeps it by itself over SSH, in CI and on a machine without a browser. See [Sign In to a Sovrium Cloud](/en/docs/login).
- **`sovrium seed --dry-run` in `if-empty` mode reports the tables it would skip.** It now counts the rows of each table, and a table that already holds some reads `would skip (N rows already present)`, the skip the real run makes, where it used to read `would create N records` for every table. A script that parsed the dry run's lines should expect the new one. See [Seeding Data](/en/docs/cli-seed).

## Upgrading from 0.34 to 0.34.3

### Behaviour that changes without a config change

- **A count filtered by an `or` group now counts every record meeting at least one condition.** It counted only the records meeting all of them. A rollup or a lookup whose `filters` is an `and` / `or` group, which stopped the server at start, now boots and applies the group.
- **A rollup over a currency field now prints in that currency.** A SUM, AVG, MIN or MAX rollup over a `currency` field takes that field's currency and display settings, in the records API (`?format=display`) and on pages, where it printed a bare number or a dollar sign before. A rollup can also declare `currency`, `precision`, `symbolPosition`, `negativeFormat` and `thousandsSeparator` itself to override them.
- **A table view filtered by `isEmpty` or `isNotEmpty` without a `value` now applies that condition.** It showed every row.
- **A `flow/stop` with `status: error` — the default when `status` is omitted — now ends the run failed.** It used to store the run `completed` — or `completed-with-errors` after a step failed under `continueOnError` — at the top level, inside a path or a loop, whatever the trigger. The run now reads `failed`, with the stop's message as its error: every automation-failure trigger watching the automation fires, operators receive the automation-failure email, the run counts toward `SOVRIUM_AUTOMATION_AUTOPAUSE`, and a form submission the automation handled is recorded failed. `continueOnError` on the stop does not change this. A synchronous webhook caller still receives the stop's `{ status, message }` answer with HTTP 200, or the answer of an earlier `webhook/response`. Give every expected early exit `status: success`, and review any alert or filter that keys on `completed`, and any failure handler that will now see these runs.
- **A synchronous `automation/call` now fails when the called automation exhausts its retries, times out or is cancelled.** It used to fail only when the called automation failed outright; in the other three endings the call was recorded `completed` with an empty result and the calling run went on. The call step now fails, and the calling run fails with it unless the step is marked `continueOnError`.
- **A form submission is recorded `failed` whenever its bound automation ends in failure.** It used to read `done` when the automation used up its retries, timed out or was cancelled; only an outright failure recorded `failed`. Such a submission now reads `failed`, with the run's error as its reason, and no longer counts toward `maxSubmissions`.
- **Single-mode data sources now apply their `filter`.** A config that relied on it being ignored binds a different record.

## Upgrading from 0.33 to 0.34

Run `sovrium validate` with 0.34 before you restart: it refuses the configs below, naming the place to change.

### Configs that are refused

- **A step named `loop` or `loops` is refused.** These two names are now the template roots for loop items: `{{loop.*}}` is the innermost loop, and `{{loops.<loop name>.*}}` is any enclosing one. `sovrium validate` and startup refuse a step with either name, at any depth, naming the step and its path. Rename the step, and every `{{loop.…}}` or `{{loops.…}}` that read its output.

### Behaviour that changes without a config change

- **An upload key that only differs from a stored key by letter case or Unicode normalisation is refused.** A key you choose — an explicit upload `path`, a signed upload, or an automation's `file/upload` — is compared with the stored keys after Unicode normalisation, and also ignoring letter case when the local storage directory is on a case-insensitive disk (the macOS and Windows defaults), which Sovrium checks when it starts. A key landing on a file another key already names is refused instead of replacing that file: an upload answers `404` or `409`, and an automation step fails. Stored keys are not rewritten and stay readable as written; on a case-sensitive disk two cased spellings remain two files.
- **`$record.<attachment>` in a row template is now an address.** On a private bucket it is a signed download link valid for one hour; on a public bucket it is the bucket's files address. It used to print the storage key. A template that built an address around it (`/api/buckets/<bucket>/files/$record.<attachment>`) now nests one address inside another: write `$record.<attachment>.key` there, or use the bare token on its own. `sovrium validate` warns on each such token and names its place in the config.
- **An automation's record steps check the files they attach.** A record step writing an attachment key must name a file stored in that column's bucket, as a write through the records API already had to. A step running as the person who triggered it (`runAs: triggering-user`) must also name a file that person may download. Otherwise the step fails and nothing is written. To attach a file a `file/upload` step stored, give that step the column's `bucket`. A step that writes as nobody — a webhook, a schedule, a record event, with no `runAs` — may attach only a file its own run stored, or an inline value; a key that existed before the run now fails the step, where it used to be written. A file stored before an approval or a wait, or by the run that called it with `automation/call`, counts as existing before the run. This includes a generated document's `ifExists: skip` with `attachTo`, which no longer attaches a file an earlier run generated. Write the file again in the run (`ifExists: overwrite`), or run the step as a person.
- **Journal and log lines stay with admins wherever they are copied.** A later step that writes `{{steps.<health>.journal}}` or a logs step's `lines` into its own output no longer shows them to a reader who is not an admin; an admin still reads the run whole.
- **A run approved after a tolerated failure ends `completed-with-errors`.** A step that failed under `continueOnError` before an approval — at the top level, in a loop or in a path — used to be forgotten once the request was approved, and the run read `completed`. Review any alert or filter that keys on `completed`.
- **An inline `{ name, content }` value is stored on every attachment column.** It is stored as a file in the column's bucket instead of being kept as text, whether a records API call or an automation's record step writes it. It is held to the bucket's and the column's upload rules, and a `name` must be one file name: a value that breaks a rule, or whose content is not base64, is refused with 400.
- **Runs that used to end `completed` now end `completed-with-errors` when a loop skipped an item.** A loop with `continueOnItemError: true` still runs past a failed item, but the run no longer reads `completed` when one was dropped. Review any alert or filter that keys on `completed`.
- **Inside nested loops, `{{loop.item}}` is the inner item.** Before, a loop inside a loop read the outer item, and a later action inside a path within a loop read an earlier one as empty. Use `{{loops.<outer loop name>.item}}` for the outer item.
- **`DATABASE_POOL_MAX` is the instance's whole PostgreSQL footprint.** It used to size the request pool alone, and a start opened about twice that many connections, plus up to ten more for its migrations. Now the request pool takes what is left once one connection for migrations and maintenance and one for each AI listener the app declares are set aside: at the same value, it serves requests with `DATABASE_POOL_MAX − 1` connections, or fewer when the app uses the AI compute or knowledge listeners. Raise the value by that much if the request pool was sized exactly for your load. A value below 2, plus one for each of those listeners, now stops the start with a message naming the minimum. See [Environment variables](/en/docs/env-vars).
- **`$record.<field>` in page text prints a date, a date-time, an amount, a percentage, a yes/no, an option or a duration formatted.** A `date`, `datetime`, `created-at`, `updated-at` or `currency` field written into a component's text — and into a confirm's title and message, a `description-list` detail, a breadcrumb's current label, and the page's title and description — now reads in the page's language and the operator time zone (a `datetime` field that declares its own `timeZone` reads in that zone): `Mar 14, 2025`, `Mar 20, 2025 at 02:05 PM`, `€1,250.50`, as a `record-field` shows it, instead of the stored value. Links, attribute values, action inputs and type-to-confirm phrases keep the stored value, and on PostgreSQL a date there is now `2025-03-14` rather than `Fri Mar 14 2025 00:00:00 GMT+0000 …`. A `record-field` with no `format` now formats in the page's language rather than always in English, and a `datetime` field with its own `timeZone` in that zone. A `percentage`, a `checkbox`, an option (`single-select`, `status`, `multi-select`) and a `duration` field are formatted the same way: `12.5%`, `Yes`, the option's label rather than its stored value, the labels joined as the page's language writes a list, and `1:30`. A record drawer's children and confirm, a kanban card and a list or search item template, which the browser fills, now print every one of these values exactly as the server does, instead of the stored value. Write `$record.<field>.raw` wherever a sentence must keep the stored value. See [Page References](/en/docs/pages-references).
- **A component with its own `dataSource` reads its own record, not the page's.** On a page bound to one record — a `collection` page, or a page with `dataSource: { mode: single }` — a component that declares its own `dataSource` used to have `$record.<field>` in its text and `props` filled from the PAGE's record first, so it printed the page record's value for a field both tables share, and nothing for one only its own table has. It now prints its own record's value. Its `dataSource` filters still read the page's record. If a bound component's text was meant to quote the page's record, move that text to a sibling or a parent that declares no `dataSource`. See [Data Binding](/en/docs/pages-data-binding).
- **A webhook run no longer keeps the values of credential headers.** `cookie`, `set-cookie`, `authorization`, `proxy-authorization`, the header a webhook's `auth` names for its key or signature, and any header whose name contains `authorization`, `cookie`, `token`, `secret`, `signature`, `api-key`, `apikey` or `password` are recorded with the value `***`. The header's name is kept, so you can still see it was sent. A step reading one of them through `{{trigger.data.headers.…}}` now reads `***`: use `{{trigger.user.*}}` to know who called, and a connection or an `$env` secret to call another service. Authentication still checks the real value before the run starts. Runs recorded before the upgrade are shown, and replayed, with the same values hidden.

## Roll back

Because migrations do not reverse, a rollback restores the pre-upgrade backup with the prior binary or image. `--force` replaces the migrated data directory and config; the backup's checksums are verified before anything is replaced:

```bash
sovrium stop
curl -fsSL https://sovrium.com/install | sh -s -- --version 0.24.0   # the version you upgraded from
sovrium restore /backups/pre-upgrade.tar.gz --force
sovrium start app.yaml
```

For **zero downtime**, run the new version as a second instance behind your proxy, verify it, then switch traffic — keeping the old instance until you are confident.

## Per-app engines

On a host that supervises several Sovrium apps with the `instance` actions, each app runs the engine its own release names rather than one binary shared by all. The host keeps one binary per version in its engine store, each release links the one it runs on, and the units start the app through that link. An app therefore moves to a new engine only when it is redeployed — built and deployed with the new version — and the apps beside it stay where they are.

A rollback to the previous release brings back the engine that release linked, together with its config. That is the one place the downgrade rule applies:

- **Never run an app on an engine older than one it has already run, except by restoring the backup taken before the move.** The newer engine may have migrated the database on its first start, and migrations do not reverse. Take a backup whenever an apply reports that it raises the app's engine, and when the new release fails, roll back and restore that backup together. Writes made between the move and the restore are lost; the app was failing in that window.
- **Rolling back to an older config is not rolling back the engine.** To return to an earlier deployment without the restore, apply its config on the newer engine the app already runs.

The **Instance Actions** article describes `engineInstall`, the `engine` an `apply` names, and `enginePrune`, which keeps the store to the versions a release still links.
